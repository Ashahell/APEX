## High Priority Items

### H1: Automated Runbook Execution

**Objective:** When alerts trigger, automatically execute predefined remediation runbooks instead of just notifying.

**Scope:** Alert actions, workflow execution, runbook library

**Design:**
```
Alert Triggered → Match Rule → Execute Runbook → Log Result → Notify Outcome
```

**Runbook Format:**
```yaml
name: restart-failed-task
trigger:
  alert_type: task_timeout
conditions:
  - task.status: running
  - task.elapsed_secs: '>': 3600
actions:
  - type: cancel_task
    target: '{{alert.task_id}}'
  - type: create_task
    input: '{{alert.original_input}}'
    priority: high
  - type: notify
    message: "Task restarted automatically"
```

**Tasks:**
- [ ] Create runbook schema and parser (`runbook.rs`)
- [ ] Add runbook repository to database
- [ ] Implement runbook executor
- [ ] Add `Runbook` action type to AlertAction enum
- [ ] Create runbook CRUD API endpoints
- [ ] Build runbook editor UI
- [ ] Add runbook templates (restart-failed, clear-cache, etc.)
- [ ] Write integration tests

**API Endpoints:**
```
GET    /api/v1/runbooks           - List runbooks
POST   /api/v1/runbooks           - Create runbook
GET    /api/v1/runbooks/:id       - Get runbook
PUT    /api/v1/runbooks/:id       - Update runbook
DELETE /api/v1/runbooks/:id       - Delete runbook
POST   /api/v1/runbooks/:id/test  - Test runbook
POST   /api/v1/runbooks/:id/execute - Manual execute
```

**Acceptance Criteria:**
- [ ] Runbooks can be created, edited, and deleted via API/UI
- [ ] Alert rules can trigger runbook execution
- [ ] Runbook execution logs to audit trail
- [ ] Manual runbook execution works
- [ ] At least 3 template runbooks included

### H2: Health Check Dashboard

**Objective:** Real-time system health overview with component-level status, not just overall health endpoint.

**Scope:** System monitoring, health aggregation, UI dashboard

**Design:**
```
┌─────────────────────────────────────────────────────────────┐
│                    System Health Overview                     │
├─────────────┬─────────────┬─────────────┬───────────────────┤
│    L2      │    L3      │    L4      │       L5          │
│   Router   │   Memory   │   Skills   │    Execution       │
│    ✅      │    ✅      │    ⚠️      │       ❌          │
│            │            │ Degraded   │    Pool Exhausted  │
├─────────────┴─────────────┴─────────────┴───────────────────┤
```

### H3: Task Retry Policies

**Objective:** Automatically retry failed tasks with configurable policies (exponential backoff, max attempts, retry conditions).

**Scope:** Task execution, deep task worker, retry logic

**Design:**
```rust
pub struct RetryPolicy {
    pub max_attempts: u32,           // 3
    pub initial_delay_ms: u64,       // 1000
    pub max_delay_ms: u64,           // 60000
    pub backoff_multiplier: f64,     // 2.0
    pub retry_on: Vec<TaskStatus>,   // [Failed, Cancelled]
    pub retry_conditions: Vec<Condition>,
}

pub enum Condition {
    ErrorContains(String),
    ErrorCode(u32),
    ElapsedLessThan(u64),
}
```

**Retry Flow:**
```
Task Failed
    ↓
Check RetryPolicy
    ↓
Attempt < Max?
  Yes → Wait (exponential backoff) → Re-execute
  No  → Mark Failed → Notify
```

**Tasks:**
- [ ] Add RetryPolicy to task creation/update
- [ ] Implement retry logic in deep_task_worker
- [ ] Add retry attempt tracking (retry_count, last_retry_at)
- [ ] Create retry policy CRUD API
- [ ] Add retry status to task view
- [ ] Build retry policy editor UI
- [ ] Write retry policy tests
- [ ] Add retry metrics to analytics

**API Endpoints:**
```
GET    /api/v1/tasks/:id/retry     - Retry failed task
PUT    /api/v1/tasks/:id/retry-policy - Set retry policy
GET    /api/v1/tasks/retry-stats   - Retry statistics
```

**Acceptance Criteria:**
- [ ] Tasks can be configured with retry policies
- [ ] Exponential backoff implemented correctly
- [ ] Retry count displayed in task details
- [ ] Manual retry works for any failed task
- [ ] Retry statistics available via API

**Files:**

### H4: Alert Correlation

**Objective:** Group related alerts to reduce noise and identify root causes faster.

**Scope:** Alert system, correlation engine, UI grouping

**Design:**
```
Alert A (CPU High) ─┐
Alert B (Memory High)─┼──▶ Correlation Group ─▶ Root Cause: Pod Overloaded
Alert C (Swap High) ─┘
```

**Correlation Rules:**
1. **Time Window**: Alerts within N minutes of each other
2. **Task Scope**: Same task_id
3. **Pattern Match**: Known failure patterns (OOM → Crash, Slow Query → Timeout)
4. **Resource Scope**: Same resource (disk, memory, CPU)

**Data Model:**
```rust
pub struct AlertCorrelation {
    pub id: String,
    pub root_alert_id: String,
    pub grouped_alert_ids: Vec<String>,
    pub correlation_type: CorrelationType,
    pub confidence: f32,
    pub created_at: DateTime<Utc>,
    pub resolved_at: Option<DateTime<Utc>>,
}

pub enum CorrelationType {
    TaskScope,
    ResourceScope,
    PatternMatch,
    TimeWindow,
}
```

**Tasks:**
- [ ] Define correlation rules engine
- [ ] Implement time-window correlation
- [ ] Implement task-scope correlation
- [ ] Add pattern-based correlation
- [ ] Create correlation API endpoints
- [ ] Update UI to show alert groups
- [ ] Add correlation metrics
- [ ] Write correlation tests

**API Endpoints:**
```
GET /api/v1/vigilant/correlations         - List correlation groups
GET /api/v1/vigilant/correlations/:id     - Get correlation details
POST /api/v1/vigilant/correlations/:id/resolve - Mark resolved
```

**Acceptance Criteria:**
- [ ] Related alerts automatically grouped
- [ ] Root cause identified with confidence score
- [ ] UI shows collapsed alert groups
- [ ] Correlation statistics in analytics

**Files:**
